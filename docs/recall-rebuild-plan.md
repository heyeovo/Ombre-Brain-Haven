# Haven 记忆召回重构与家族聚类方案

> 状态：方案已确认，尚未开始代码实施  
> 日期：2026-08-27  
> 关联交接：`docs/2026-08-27-recall-rebuild-handoff.md`  
> 现有实现说明：`docs/recall-pipeline.md`

## 1. 背景与结论

Haven 当前动态召回已经具备关键词、向量语义、精确锚点、query planner、admission gate、会话去重和 Debug 数据，但真实使用中的召回质量明显失衡：

- 很多只在字面上碰巧匹配的桶被注入；
- 很多语义和关键词都明显相关的桶被硬规则拒绝；
- query planner 不可用或提词失真时，错误的 axis / anchor 仍拥有一票否决权；
- Gateway Debug 信息完整，但过于底层，不适合持续人工验收。

2026-08-27 对 session `ob2-20260821-mu4pah` 的 48 轮线上 Debug 做了只读审计：

- 16/48 轮发生召回，共注入 22 个桶；
- 14/22 个注入桶通过 `non_explicit_query` 放行；
- 778 个候选被拒，其中 `activated_axis_mismatch` 514 个、`anchor_must_group_missing` 89 个、`auto_vague_query_without_topic` 53 个；
- 31/48 轮出现 `query_planner_dehydration_unavailable`；
- 存在“关键词为 1、语义为 0 仍注入”和“高语义、高关键词候选被硬拒”的对照案例。

因此，本项目不继续逐条追加 admission 规则。重构方向是将召回拆成清晰阶段、先建立可观测与验收能力，再逐步修复平面桶召回，最后接入家族聚类和少量有明确语义的关系边。

## 2. 已确认的产品原则

1. 默认宁可少召回，也不要注入与当前上下文无关的记忆。
2. 用户明确表达“记得、上次、之前、那次、帮我找、搜某件事”等回忆或搜索意图时，应积极检索，不能被低质量 axis / anchor 全部拦截。
3. “是否需要长期记忆”和“哪个桶最相关”是两个问题，必须分开判断。
4. 关键词单独命中默认不足以自动注入；唯一名称、稳定别名或其他强直接证据可以例外。
5. axis、anchor、topic evidence 主要作为排序证据，不应普遍拥有一票否决权。
6. query planner 不可用时必须有明确降级路径，不能生成低质量规则结果后继续执行强硬拒绝。
7. 家族聚类和关系边先以 shadow mode 运行，稳定前不影响正式注入。
8. 家族层不能取代直接桶检索，两条候选路径必须并行存在。
9. 历史事件保持原貌；偏好、习惯、状态类记忆允许随时间演变，但不能覆盖旧事实。
10. 每次召回算法调整必须能用固定验收样本比较，不能只靠单轮肉眼感觉。

## 3. 目标与非目标

### 3.1 目标

- 建立面向人类判断的“召回透镜”，将现有 Debug 数据变成可检验的召回轨迹。
- 将召回改造成“必要性判断 → 候选检索 → 证据融合与排序 → 最终注入”的分层管线。
- 收紧错误注入，同时减少明显相关候选被硬规则误杀。
- 为未来家族聚类、家族摘要和关系边扩展预留统一候选接口。
- 建立人工标注、离线回放、shadow 对比和渐进发布能力。

### 3.2 非目标

- 不在第一阶段直接实现 GraphRAG 全套能力。
- 不为所有桶两两生成关系边。
- 不立即引入每条消息都调用一次额外 LLM 的召回必要性 agent。
- 不在没有观测基线时同时重写候选搜索、准入、聚类和注入。
- 不用家族摘要代替原始桶，也不覆盖历史记忆。

## 4. 目标召回架构

```text
用户消息 + 最近对话上下文
        │
        ▼
阶段 A：召回必要性判断
  - none：本轮不需要长期记忆
  - explicit：用户明确要求回忆/搜索
  - contextual：需要外部记忆才能理解当前指代或延续
        │
        ▼
阶段 B：并行候选检索
  ├─ 直接桶：关键词 / 语义 / 精确锚点 / 稳定别名
  ├─ 家族：家族摘要 / 家族名称 / 家族成员代表
  └─ 关系扩展：从高可信种子沿允许关系扩展一跳
        │
        ▼
阶段 C：统一证据融合与排序
  - 记录所有正向证据、负向证据和来源路径
  - axis / anchor / topic evidence 改为软证据为主
  - 仅保留少量明确硬拒绝
        │
        ▼
阶段 D：最终注入判断
  - 可注入 0～2 个具体桶，或一份家族摘要
  - 会话重复、token 预算和内容多样性在此处理
        │
        ▼
模型上下文 + 完整召回轨迹
```

### 4.1 保留的硬拒绝

硬拒绝只用于能够明确证明“不应该进入”的情况：

- 被排除的 domain；
- archived / resolved 等不参与动态召回的状态；
- session hard exclude 或语义重复；
- profile 隔离不匹配；
- 与查询存在明确冲突的候选；
- 不允许参与该召回层的记忆类型。

`activated_axis_mismatch`、`discriminative_anchor_missing`、`anchor_must_group_missing`、`query_topic_evidence_missing` 不再默认作为普遍硬拒绝。具体降级方式必须在观测台和固定样本上验证后决定。

### 4.2 Planner 降级契约

query planner 成功时，可以提供意图、查询重写、axis 和 anchor 证据。planner 超时、模型不可用或 dehydration 失败时：

- Debug 必须明确标记 degraded；
- 不得让降级产生的 axis / must groups 执行强硬否决；
- 明确回忆请求继续走直接检索；
- 非明确请求采用更保守的注入策略；
- 观测台分别显示 planner 原始结果和降级结果。

## 5. 召回透镜

### 5.1 定位

召回透镜是面向产品判断和持续验收的工作台，不替代 Gateway 原始 Debug。Gateway 继续提供完整工程数据；Dashboard 提供一眼可读的轨迹、筛选、标注和对比。

初期优先复用现有 `GET /gateway/api/debug/injections` 数据，不为展示需要提前改召回行为。

### 5.2 每轮展示

- 用户消息、时间、session、round、引擎路径；
- 是否需要召回及判断理由；
- planner 是否成功、是否降级、错误类型；
- 原始 query、search query、residue terms、axis、anchor；
- 候选按来源分组：直接桶、家族、关系扩展；
- 每个候选的关键词、语义、融合分、证据标签；
- 关系扩展必须显示完整路径；
- 最终状态：注入、拒绝、去重、低于阈值；
- admission reason 和真正生效的硬拒绝；
- 最终注入文本及 token 预算。

### 5.3 规则中文解释

召回透镜不能只展示内部英文规则码。每个 admission reason、planner 状态和主要 evidence label 都需要统一的中文产品解释，并说明：

- 系统在判断什么；
- 为什么这条规则会影响当前候选；
- 本轮效果是放行、拒绝，还是仅参与评分。

界面默认显示中文名称和一句话解释，英文内部码作为次要技术信息保留，方便排障和代码定位。解释必须支持点击展开，不能只依赖桌面端 hover；手机端同样可读。

规则说明使用集中维护的映射表，禁止把解释文字散落在各个卡片组件中。未知规则不能静默隐藏，统一显示原始码并标记“尚未收录中文说明”。

第一版至少覆盖当前线上已出现的：

| 内部规则码 | 中文产品解释 |
|---|---|
| `non_explicit_query` | 用户没有明确要求回忆，但系统仍认为候选可以注入；这是当前主要的宽松放行通道。 |
| `topic_evidence` | 候选包含了系统认可的当前话题证据，因此通过准入。 |
| `high_confidence_direct_edge` | 存在高可信的直接关联证据，因此通过准入。 |
| `activated_axis_mismatch` | 候选没有匹配系统从本轮消息提取出的核心主题词，因此被拒绝。 |
| `anchor_must_group_missing` | 系统要求的一组关键锚点没有全部满足，因此被拒绝。 |
| `planner_must_terms_missing` | query planner 指定的必需词没有命中，因此被拒绝。 |
| `discriminative_anchor_missing` | 候选没有覆盖系统认为最能区分主题的稀有词，因此被拒绝。 |
| `auto_vague_query_without_topic` | 系统认为本轮表达过于模糊，无法确认要回忆的具体主题。 |
| `no_hard_evidence` | 候选有一定分数，但没有任何被现有规则认可的强证据。 |
| `semantic_only` | 候选主要只有语义相似，没有关键词、锚点等额外支持。 |
| `low_recall_evidence` | 候选的综合召回证据不足。 |
| `session_hard_exclude` | 候选在当前会话中已被硬排除，通常用于避免重复注入。 |
| `tech_domain_without_query_anchor` | 候选属于技术内容，但本轮问题没有明确技术锚点。 |
| `relationship_background_without_query_topic_evidence` | 候选只是关系背景记忆，没有匹配本轮的具体话题证据。 |
| `query_topic_evidence_missing` | 候选没有包含系统要求的本轮话题证据。 |
| `query_planner_dehydration_unavailable` | 用于提炼查询意图的 planner 当前不可用，本轮正在走降级路径。 |

### 5.4 人工标注

每轮和每个候选至少支持以下判断：

- 正确召回；
- 错误召回；
- 本应召回但遗漏；
- 本轮不应召回。

标注数据必须由 Haven 持久化并保持 `profile_id` 隔离，不能只存在浏览器 `localStorage`。第一版如果只做只读透镜，可以暂缓持久化标注，但不能把临时本地状态当作最终实现。

### 5.5 主要筛选与汇总

- session / round / 时间；
- 有召回 / 无召回；
- planner degraded；
- admission reason；
- 关键词单独注入；
- 高分被拒；
- 人工标注结果；
- 当前算法与 shadow 算法的差异。

## 7. 家族聚类

### 7.1 家族的职责

家族是多个相关桶的组织层和检索入口，不是简单标签，也不是原始记忆的替代品。

建议至少区分：

- 主题/偏好家族：游戏偏好、内容偏好；
- 习惯/状态家族：睡眠、饮食、工作节奏；
- 共同经历家族：一起干活、游戏、纪念日；
- 关系发展家族：重要阶段和反复出现的关系主题；
- 技术项目家族：OB、Dashboard、部署与迁移。

一个桶允许属于多个家族。家族记录成员、代表桶、摘要、更新时间和来源，但不覆盖成员原文。

### 7.2 动态信息

偏好、习惯、当下状态需要表达演变：

- 当前仍成立；
- 新出现；
- 强化或减弱；
- 与旧状态冲突；
- 已被后续事实更新。

家族摘要必须能够追溯到具体桶，不能生成无法验证的独立事实。

### 7.3 接入召回

第一阶段只计算候选家族，不影响召回。稳定后：

- 广义问题可以优先使用家族摘要；
- 具体事件问题仍优先直接检索具体桶；
- 家族命中只负责扩展少量成员候选；
- 家族分类错误不能阻断直接桶路径；
- 所有扩展结果继续参与统一排序和最终注入判断。

## 8. 关系边

Haven 已有关系边机制，但目前桶之间基本没有建立可用于召回的真实关系，因此实施时按“图数据尚未建立”处理。

不为普通主题相似建立大量两两关系。主题相似由家族和向量承担；关系边只表达更具体的语义：

- 同一事件；
- 后续发展；
- 因果；
- 状态更新；
- 冲突或修正；
- 明确的人物、地点、物品关联。

关系边至少需要：类型、方向、来源、证据、置信度、创建方式、审核状态和时间信息。

召回时只允许从高可信种子出发，按允许的边类型扩展一跳；扩展桶不能仅凭“存在关系”自动注入，仍需统一排序。初期只在召回透镜中显示 shadow 候选及完整路径。

## 9. 分阶段实施

### Phase 0：召回透镜最小版与基线

- 在 Dashboard 建立只读召回透镜；
- 复用现有 Gateway Debug API；
- 能加载指定 session 的完整轮次；
- 展示 query、planner 状态、候选、分数、拒绝原因和最终注入；
- 导入并人工核对首批固定案例；
- 不改变任何正式召回行为。

### Phase 1：召回必要性与 planner 降级

- 将 recall necessity 从 bucket admission 中独立出来；
- 明确 explicit / contextual / none；
- planner 不可用时关闭错误 axis 的硬否决能力；
- shadow 对比新旧决定，不直接切换正式路径。

### Phase 2：统一准入与排序

- 收紧或替换 `non_explicit_query`；
- 把主要 axis / anchor / topic gate 转为软证据；
- 保留少量明确硬拒绝；
- 用固定验收集比较误召和漏召；
- 逐步启用新路径，并保留可回退开关。

### Phase 3：家族聚类 shadow mode

- 定义家族数据结构和持久化迁移；
- 对现有桶生成候选家族归属和摘要；
- 在记忆地图/召回透镜中展示，不参与正式注入；
- 支持人工纠正和重新计算；
- 验证时间变化、冲突和多家族归属。

### Phase 4：家族辅助召回

- 家族检索与直接桶检索并行；
- 家族只扩展有限成员；
- 广义问题可以注入家族摘要；
- 对具体事件保持直接桶优先；
- 按人工验收结果逐步开启。

### Phase 5：关系边生成与一跳扩展

- 只生成高价值的明确关系；
- 先 shadow 展示路径和候选；
- 审核关系质量后允许少量边参与候选扩展；
- 禁止无界多跳扩散和仅凭边存在直接注入。

### Phase 6：评估额外 LLM 判断

只有规则和统一排序仍无法可靠判断召回必要性时，才评估轻量 LLM agent。必须测量延迟、token、可用性和模型故障降级，不默认每轮调用。

## 10. 验收指标

每个阶段同时观察：

- 错误注入率；
- 明确回忆请求的命中率；
- 高相关候选被硬拒的比例；
- 关键词单独注入比例；
- planner degraded 时的行为；
- 每轮注入数量和 token；
- shadow 与正式结果差异；
- 人工标注的一致性。

第一轮算法修复的最低验收是：本方案第 6 节六个案例全部达到预期，同时不得让普通闲聊的召回频率明显上升。

## 11. 风险控制

- 每一阶段独立开关，支持退回现有行为；
- shadow 数据与正式注入结果必须同时记录；
- 数据库迁移可重复执行，并兼容已有库和 `profile_id` 隔离；
- 家族摘要、自动边和人工标注都必须可追溯来源；
- 先限制候选数量和一跳扩展，禁止图扩散失控；
- 不把外部模型可用性设为唯一运行前提；
- Dashboard 展示不得泄露 Bearer token 或其他密钥。

## 12. 跨仓库职责

### Haven

- 召回轨迹和 Debug API；
- 人工标注、家族和关系数据的持久化；
- 召回必要性、候选检索、统一排序和注入；
- shadow 结果和正式结果记录；
- 数据迁移与隔离测试。

### ob-dashboard2

- 召回透镜；
- 记忆地图和家族审核界面；
- 标注、筛选、对比和路径展示；
- 只通过服务端 API 访问 Haven，不向浏览器暴露密钥。

## 13. 尚未确认的设计项

以下内容在对应实施窗口再定，不应由本方案提前锁死：

- recall necessity 第一版采用纯规则还是现有 planner 结果组合；
- 统一排序公式和具体阈值；
- 人工标注的最终表结构；
- 家族生成使用聚类算法、LLM，还是两者组合；
- 家族摘要刷新时机；
- 允许参与一跳扩展的关系类型；
- 额外 LLM 判断是否值得成本。

这些决策都必须先通过召回透镜和固定验收集验证，再进入正式召回路径。
